## What We Built

A **queue-worker agentic workflow** using:
- **DBOS SDK v4** (TypeScript) — durable execution via Postgres
- **Express** — HTTP API server (enqueues via `DBOSClient`)
- **Separate worker process** — picks up workflows from Postgres queue
- **Google Gemini 3 Flash** (via Vercel AI SDK v6) — real LLM for structured analysis
- **SQLite** — business data (sales in, insights out)

**Flow:**
```
POST /api/analyze
  → DBOSClient.enqueue("analyzeYear", year)     [server — no workflow code]
  → Postgres queue row inserted
  → Worker polls (FOR UPDATE SKIP LOCKED)
  → Workflow: readSalesData → aggregateSales → runAnalysisAgent → writeInsights
  → GET /api/analyze/:id → poll result
```

## What We Explored

### 1. DBOS Architecture (hands-on)

**Two-database design:**
- `dbos_sales` — app database (business tables)
- `dbos_sales_dbos_sys` — DBOS system database (workflow_status, transaction_outputs, queue)

**Key tables in `_dbos_sys`:**
```sql
SELECT workflow_uuid, status, name FROM dbos.workflow_status;
SELECT workflow_uuid, function_id, function_name FROM dbos.transaction_outputs;
```

**State machine:** `ENQUEUED → PENDING → SUCCESS | ERROR`

**DBOS.logger vs console.log:**
- `DBOS.logger` adds timestamp + version hash + log level — use inside workflow/step context (worker process after `DBOS.launch()`)
- `console.log` is correct for the server process (uses `DBOSClient`, no `DBOS.launch()`)

**Workflow registration in v4:**
```typescript
// Import triggers module execution → decorators/registerWorkflow run → registration happens
import { analyzeYearWorkflow } from "./workflows/analyzeSales";
DBOS.registerWorkflow(analyzeYearFn, { name: "analyzeYear" });
```

**Closure pattern for steps:**
```typescript
// v4: DBOS.runStep() takes a zero-arg closure (thunk) — bind args via closure capture
const rows = await DBOS.runStep(() => readSalesData(year));
//           ^^^ NOT: DBOS.runStep(readSalesData, year)
```
→ DBOS just calls `fn()` internally — it doesn't need to know about args, only the output matters for replay.

### 2. DBOS Distributed Model (researched + validated)

**Queue enables multi-worker pickup** (corrected earlier assumption):
```
Server → DBOSClient.enqueue() → Postgres queue table
Worker A, Worker B, Worker C → all poll same queue
→ FOR UPDATE SKIP LOCKED — exactly-once pickup, no broker needed
```

**Workflow definitions live only in the worker.** Server never imports workflow code — enqueues by string name only. This is the clean separation.

**Without Conductor (free tier workaround):**
- K8s StatefulSet with a single replica = deterministic pod identity, auto-restart recovery
- Conductor free tier = max 1 executor (dev only)
- Production = paid Conductor license OR implement a recovery cron (`DBOSClient.listWorkflows(status: "PENDING")` → re-enqueue orphans)

### 3. DBOS vs Temporal — Key Difference

| | DBOS | Temporal |
|---|---|---|
| Infrastructure | Postgres only (no extra server) | Temporal server (separate process) |
| Distributed | Via queue (all workers share Postgres) | Native — any worker picks up any workflow |
| Recovery | `DBOS.launch()` on same process | Any worker picks up stranded workflows |
| Observability | Conductor (paid for multi-executor) | Temporal Web UI (free, built-in) |
| Code style | Plain async functions + `DBOS.runStep()` | Activities + Workflows (separate concepts) |
| Best for | Simple–medium durable workflows, low ops overhead | Complex distributed systems, fintech, high scale |

**Reference:** https://www.dbos.dev/dbos-transact (DBOS vs Temporal comparison section)

### 4. Control Flow in DBOS Workflows

DBOS workflows are **plain TypeScript async functions** — no special DSL. This is a key selling point.

```typescript
// Branching
if (revenue > 1_000_000) { /* full analysis */ } else { /* lite */ }

// Loops — MUST use unique step names per iteration
for (const month of months) {
  await DBOS.runStep(() => analyzeMonth(month), { name: `analyzeMonth-${month}` });
}

// Parallel — Promise.allSettled (NOT Promise.all)
const results = await Promise.allSettled([
  DBOS.runStep(() => analyzeRegion("NA"),   { name: "region-NA" }),
  DBOS.runStep(() => analyzeRegion("EMEA"), { name: "region-EMEA" }),
]);

// Parallel fan-out (sequences in parallel) → child workflows
const handles = months.map(m => DBOS.startWorkflow(analyzeMonthWorkflow, { queueName: "q" })(m));
const results = await Promise.all(handles.map(h => h.getResult()));
```

**Critical rule:** You cannot start/enqueue workflows from inside steps — only from workflow functions.

**Reference:** https://docs.dbos.dev/typescript/tutorials/workflow-tutorial

### 5. Vercel AI SDK v6 — Structured Output Pattern

`generateObject` is **deprecated** in v6. Use `generateText` + `Output.object`:

```typescript
import { generateText, Output } from "ai";
import { google } from "@ai-sdk/google";
import { z } from "zod";

const AnalysisSchema = z.object({
  summary:         z.string().describe("2-3 sentence executive summary"),
  topProduct:      z.string().describe("Best-selling product by revenue"),
  recommendations: z.array(z.string()).describe("3 actionable recommendations"),
  riskFlags:       z.array(z.string()).describe("Risk signals, empty if none"),
});

const { experimental_output: result, usage } = await (generateText as any)({
  model: google("gemini-flash-latest"),
  output: (Output.object as any)({ schema: AnalysisSchema }),
  prompt: `You are a senior analyst. Analyse: ${JSON.stringify(data)}`,
});
// usage.inputTokens, usage.outputTokens (renamed in v6 from promptTokens/completionTokens)
```

**What happens under the hood:**
1. Zod schema → JSON Schema (automatic)
2. Sent to Gemini as `generationConfig.responseSchema` constraint
3. Gemini response is constrained to that shape
4. SDK parses + validates before returning
5. `.describe()` fields are sent as `"description"` in the JSON schema — model uses them

**The TS2589 fix** (type instantiation too deep):
```typescript
// Cast the function call + restore type on return
const { experimental_output: object } = await (generateText as any)({ ... });
return object as MyOutputType;  // type safety restored here
```

### 6. LLM + Orchestration Landscape (2026 State)

**The winning pattern (industry consensus):** Narrow agents wrapped in durable orchestrators.
- Orchestrator = DBOS or Temporal (handles durability, retry, state)
- Agent = a single LLM call with a Zod-constrained output schema
- Tools = plain TypeScript functions called via `DBOS.runStep()`

**TypeScript SDK landscape:**

| SDK | What it does | When to use |
|---|---|---|
| `ai` (Vercel AI SDK) | Unified LLM calls, structured output, tool calling | Default choice for TS — provider-neutral, clean API |
| `@ai-sdk/google/openai/anthropic` | Provider adapters | Swap one import to change model provider |
| LangGraph JS | Stateful agent graphs (nodes + edges) | Complex multi-agent routing, explicit state machines |
| OpenAI Agents SDK TS | OpenAI-native multi-agent with handoffs | OpenAI-only, GA March 2026 |
| Mastra | All-in-one TS agent platform with Studio UI | When you want batteries-included + visual debugger |
| LlamaIndex TS | RAG-first — document retrieval pipelines | Core problem is retrieval, not orchestration |

**Key insight:** Vercel AI SDK is the engine (how LLM gets called). LangGraph is the chassis (how agent logic flows). DBOS is the foundation (durability + recovery). You can run the engine standalone for simple cases.

## Key Lessons (blog-worthy)

1. **DBOS makes durable execution feel like plain code** — no workflow DSL, no separate concept of "activities". Just annotate functions. The tradeoff: less visibility than Temporal without Conductor.

2. **The `as any` cast pattern for complex generics** — when SDK types are too deep for TS inference (`TS2589`), cast the function call to `any` and restore type safety on the return. Don't fight the compiler on library internals.

3. **`.describe()` on Zod fields is not optional** — it's your prompt engineering for structured output. The description goes into the JSON schema and the model uses it to understand intent.

4. **`Promise.allSettled` not `Promise.all` for parallel DBOS steps** — `Promise.all` rejects immediately on first failure, losing context. `Promise.allSettled` lets all steps complete and gives you granular per-step results.

5. **Worker startup order matters** — `DBOS.launch()` must complete before `registerQueue()`. `bootstrapAndGetDb()` must run before any workflow tries to query SQLite. Sequence: DB bootstrap → DBOS launch → queue register → signal handlers → block.

6. **Two processes, two concerns** — server knows zero workflow code. Worker owns all workflow code. This is the correct separation for scalability: scale workers independently, deploy new workflow versions by updating only the worker image.

7. **`DBOS.logger` vs `console.log`** — use `DBOS.logger` inside the worker process (after `DBOS.launch()`). It adds workflow context, version hash, timestamp automatically. Server uses `console.log` — no DBOS context available there.
