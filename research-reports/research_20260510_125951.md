# Research Report: Auto-Fix Vulnerability Agent — From Detection to PR

**Date:** 2026-05-10
**Query:** How to build a security/vulnerability agentic workflow that goes beyond detection — auto-fixing vulns by generating PR diffs against GitHub, balancing deterministic and agentic steps in a durable orchestration framework.

---

## Executive Summary

Building a vulnerability agent that **auto-fixes** code (not just detects) requires a carefully layered architecture where deterministic steps (scanning, policy evaluation, dependency resolution, PR creation) wrap agentic steps (fix generation, triage, impact analysis) with strict guardrails. The industry is converging on a **three-tier confidence model**: (1) auto-merge for safe dependency bumps with CI validation, (2) human-reviewed PRs for AI-generated code fixes, and (3) manual-only for complex multi-file remediation. Key data points:

- **Only 24.8%** of LLM-generated security patches achieve full correctness (PatchEval benchmark, ByteDance 2025)
- **51.4%** of AI patches apply fundamentally incorrect repair strategies
- **Bot PRs get accepted at 37%** vs 73% for humans — trust is the bottleneck
- **Snyk Agent Fix achieves ~80% accuracy** through multi-model + static analysis re-validation
- **Copilot Autofix cuts remediation time by 7-12x** (SQL injection: 18 min vs 3.7 hours)
- **GitHub App installation tokens** (8-hour rotation) are the gold standard for automated agents
- **Git Trees API** enables atomic multi-file commits — critical for complex fixes
- **DBOS patterns map directly**: `runStep` for scanning, `runStep+retry` for LLM calls, `DBOS.recv()` for human approval gates, child workflows for parallel fix generation

The sweet spot for 2026: **hybrid orchestration** — deterministic guardrails around bounded agentic reasoning, with earned autonomy through demonstrated competence.

## 1. The Auto-Remediation Landscape: What Exists Today

The market has bifurcated into **deterministic fixers** (version bumps) and **agentic fixers** (code-level patches), with most tools now offering both tiers.

### 1.1 Tool Strategies Compared

| Tool | Fix Approach | Deterministic | Agentic (AI) | Key Metric |
|------|-------------|--------------|--------------|------------|
| **Dependabot** | Min-version bump to patched release | ✅ Core | ✅ Coding agent for complex fixes (Apr 2026) | 54% merge rate; Compatibility Scores from millions of CI runs |
| **Snyk Fix** | Upgrade / pin / precision patch | ✅ Core | ✅ Agent Fix (LLM + re-test via Snyk Code engine) | ~80% AI fix accuracy; generates up to 5 candidate fixes |
| **Copilot Autofix** | CodeQL + GPT → code suggestions | ❌ | ✅ Core | 460K alerts fixed in 2025; SQL injection fix: 18 min vs 3.7 hrs |
| **Socket.dev** | Version bump + test validation | ✅ Core | ❌ | `--autopilot` mode: test → PR → auto-merge if tests pass |
| **Mend Renovate** | Min-version resolving all open CVEs | ✅ Core | ❌ | Merge confidence scoring; least-change principle |
| **Snyk Evo** (2026) | Multi-agent orchestration | ✅ Guardrails | ✅ Workflow Agent + specialized Task Agents | First agentic security system with agent orchestration |

### 1.2 The Confidence Spectrum

Tools handle the "when to auto-merge vs review" decision differently:

- **Dependabot**: Compatibility Score badge (Green = safe to merge based on aggregate CI data; Red = proceed with caution)
- **Snyk Breakability Analysis**: 🟢 Low Risk (auto-merge candidate) → 🟡 Medium (caution) → 🔴 High (requires sprint planning)
- **Socket.dev**: Binary — tests pass = merge; tests fail = rollback. No ambiguity.

**Critical insight**: Developers need *quantitative evidence* that a change won't break anything, not just a bot's assertion. Small, focused PRs with clear explanations drastically outperform bulk dependency updates.

### 1.3 Known Failure Modes

- **Breaking changes from major version bumps** — auto-updating a major library version can break legacy modules
- **Transitive dependency blindness** — Snyk cannot fix transitive deps automatically; only provides recommendations
- **AI fix regressions** — Snyk Agent Fix warns that suggestions "might generate code that results in the application not working properly"
- **Test-only validation gaps** — unit tests may not cover attack surface variants; code-similarity metrics don't substitute for exploit-based validation
- **Inter-file fix limitations** — Snyk Agent Fix currently does not support inter-file fixes

## 2. LLM-Powered Fix Generation: Architecture & Accuracy

### 2.1 How AI Fix Tools Work

**Copilot Autofix Architecture:**
- Combines CodeQL scanning engine + GPT-5.3-Codex
- Leverages SARIF alert data augmented with source code snippets to craft LLM prompts
- Users can accept, edit, or reject suggestions — never auto-applied

**Snyk DeepCode AI Fix:**
- Multiple models trained on millions of permissively-licensed open source projects with verified fixes
- Patent-pending CodeReduce technology for accuracy
- Static analysis engine + symbolic AI analyses filter incorrect fixes and hallucinations
- Generates up to 5 candidate fixes per vulnerability

**FixAgent (Multi-Agent Academic Framework):**
- Hierarchical 3-level architecture:
  - **L1**: Locator + Fixer for simple, single-file bugs
  - **L2**: Adds Slicer + Summarizer with file-level context
  - **L3**: Seven specialized agents for cross-file dependencies

### 2.2 What Context the LLM Needs

The quality of a fix correlates directly with context quality, not model size:

1. **Vulnerability metadata** — CVE description, CWE pattern, CVSS score, flow path from scanner
2. **Static analysis data** — CodeQL/Semgrep/Joern output with call paths and vulnerable function bodies
3. **Surrounding code** — function-level + one layer of cross-file dependencies (global vars, method signatures)
4. **Fix patterns from similar vulnerabilities** — retrieved via hybrid BM25 + dense passage retriever
5. **Dependency graph** — which packages are affected, transitive relationships

**Critical finding**: Without typedef definitions, a baseline patching agent failed 15/20 times; including them achieved 18/20 successes. It's not about smarter LLMs — it's about giving the right context.

### 2.3 Patch Format: Diff vs AST vs Hybrid

| Approach | Accuracy | Pros | Cons |
|----------|----------|------|------|
| **Unified diff** | 70-80% on complex files | Only changes intended sections; GPT-4.1 specifically trained on this format | Pattern matching failures on evolved codebases; context line mismatches in multi-turn |
| **AST-level** | Higher precision | Captures semantic intent; avoids breaking changes | More complex tooling; harder to generate |
| **Hybrid semantic** (Morph Fast Apply) | Highest | No line-number matching; understands code structure; merges at semantic level | Newer, less battle-tested |

**Recommendation for PoC**: Start with unified diff format (well-supported by LLMs) + Zod schema validation. Graduate to semantic merging for production.

### 2.4 Published Accuracy Rates

**Security-Specific (PatchEval benchmark — 1,000 CVEs, 65 CWE categories):**
- Only **24.8%** of patches achieve full correctness
- **51.4%** apply fundamentally incorrect repair strategies
- **10.3%** pass all functional tests but remain exploitable (deceptive "correct" patches)
- CWE-20 (Input Validation): 95% compile, **0% actually fix** the vulnerability
- CWE-611 (XXE): 80% compile, **40% fix** rate

**General Code (SWE-bench):**
- GPT-5.5 leads at 82.6% on SWE-bench Verified
- SWE-Bench Pro (harder): top models score only ~23%

**Industry tools:**
- Snyk Agent Fix: ~80% accuracy (with multi-model + static re-validation)
- Google Gemini on fuzzing bugs: 15% fix rate (fully automated, no human review)
- LLMs introduce vulnerabilities at **9x the rate of human developers** (SWE-bench analysis)

### 2.5 Risks of AI-Generated Security Fixes

| Risk | Frequency | Impact | Mitigation |
|------|-----------|--------|------------|
| **Incorrect repair strategy** | 51.4% | Fix doesn't address root cause | Multi-candidate generation + re-scan |
| **Functional breakage** | ~30% | Tests fail after fix | Run full test suite before PR |
| **Deceptive security failure** | 10.3% | Passes tests but still exploitable | PoC exploit validation + re-scan with multiple tools |
| **Hallucinated APIs** | 3-27% | Code references non-existent functions | Type checking + compilation step |
| **Missing imports** | Common | Fix uses sanitization without importing library | AST validation of imports |
| **Localization failure** | 60-78% | Patches wrong location in code | Static analysis-guided localization (CodeQL flow paths) |

## 3. GitHub API Surface for Programmatic Fixes

### 3.1 The API Flow (REST, using Octokit)

```
┌─────────────────────────────────────────────────────────┐
│  DETERMINISTIC: GitHub API Choreography                  │
│                                                          │
│  1. GET  /repos/{o}/{r}/git/refs/heads/main             │
│     → get base commit SHA                                │
│                                                          │
│  2. POST /repos/{o}/{r}/git/refs                        │
│     → create branch: refs/heads/fix/CVE-2026-xxxx       │
│                                                          │
│  3. POST /repos/{o}/{r}/git/blobs  (per file)           │
│     → upload fixed file content → blob SHA               │
│                                                          │
│  4. POST /repos/{o}/{r}/git/trees                       │
│     → atomic tree with all changed files                 │
│     (limit: 100K entries, 7MB)                           │
│                                                          │
│  5. POST /repos/{o}/{r}/git/commits                     │
│     → commit referencing tree + parent                   │
│                                                          │
│  6. PATCH /repos/{o}/{r}/git/refs/heads/fix/CVE-...     │
│     → update branch to new commit                        │
│                                                          │
│  7. POST /repos/{o}/{r}/pulls                           │
│     → create PR (as draft initially)                     │
│                                                          │
│  8. GET  /repos/{o}/{r}/pulls/{n}                       │
│     → trigger + poll mergeable status                    │
│                                                          │
│  9. GET  /repos/{o}/{r}/commits/{sha}/check-runs        │
│     → poll CI status every 10-30s                        │
│                                                          │
│  10. PUT /repos/{o}/{r}/pulls/{n}/merge  (if approved)  │
│      → merge when CI green + human approval              │
└─────────────────────────────────────────────────────────┘
```

### 3.2 Authentication

**GitHub App installation tokens are the gold standard:**

| Factor | PAT | GitHub App |
|--------|-----|------------|
| Token lifetime | 7-90 days | 8 hours (auto-rotate) |
| Rate limit | 5,000/hr | 5,000-15,000/hr |
| Identity | Impersonates user | Shows as app (no seat consumed) |
| Blast radius | User's full access | Only installed repos |
| Revocation | Manual | Centralized |

### 3.3 Rate Limits

- **Primary**: 5,000 req/hr (base); 15,000/hr for GitHub Enterprise Cloud
- **Secondary (abuse prevention)**: 900 points/min (GET=1pt, POST/PATCH=5pts)
- **Handling**: Octokit `@octokit/plugin-throttling` + `@octokit/plugin-retry` — queue and backoff automatically

### 3.4 Key Gotchas

- **Merge conflict detection is async** — must call `GET /pulls/{n}` to trigger computation; poll for `mergeable` field (can be `null` while computing)
- **Git Trees API returns subtree objects for directories** — must remove these before POST or you get 500 errors
- **Can inline file content in tree POST** — skip blob creation for small files (optimization)
- **GitHub Actions generates check runs, not commit statuses** — poll Check Runs API, not the older statuses API

### 3.5 SARIF Integration (Closing the Loop)

After fix merges:
- Upload SARIF scan results: `POST /repos/{o}/{r}/code-scanning/sarifs` (max 10MB gzip)
- Dismiss alerts: `PATCH /repos/{o}/{r}/code-scanning/alerts/{n}` with `{"state":"dismissed","dismissed_reason":"fixed"}`
- Dependabot alerts don't have a clean "this CVE affects default branch" flag — requires filtering

### 3.6 SDK Choice

```typescript
npm install octokit @octokit/auth-app @octokit/plugin-throttling @octokit/plugin-retry
```

Octokit provides full TypeScript types, automatic token management for GitHub Apps, and built-in rate limit handling.

### 4.3 Human-in-the-Loop Gate Design

```typescript
// DBOS pattern: recv() with timeout for human approval
async function awaitApproval(
  finding: TriagedFinding,
  prUrl: string
): Promise<"approved" | "rejected" | "timeout"> {
  // Auto-approve if low risk + high confidence
  if (finding.confidence >= 0.9 && finding.severity <= "MEDIUM"
      && finding.fixType === "version-bump" && finding.ciPassed) {
    return "approved";
  }

  // Notify team (Slack/email) — deterministic step
  await DBOS.runStep(() => notifyForApproval(finding, prUrl));

  // Wait for human response via DBOS.recv()
  const timeout = finding.severity === "CRITICAL" ? 4 * 3600 : 72 * 3600;
  const response = await DBOS.recv<string>("approval", timeout);

  if (!response) {
    await DBOS.runStep(() => escalateToOnCall(finding));
    return "timeout";
  }
  return response as "approved" | "rejected";
}
```

### 4.4 Parallel vs Sequential Fix Strategy

| Scenario | Strategy | Reason |
|----------|----------|--------|
| 10 independent vulns in different deps | 10 separate PRs | Isolated review, independent CI, can merge incrementally |
| 3 vulns in same dependency (transitive chain) | 1 combined PR | Upgrading once resolves all three; avoid conflicting bumps |
| Mixed: 7 independent + 3 in same dep | 7 + 1 = 8 PRs | Group transitive, separate independent |
| Many low-severity version bumps | Batched PR (weekly) | Reduce PR noise; scheduled cadence |

**DBOS pattern**: Use `DBOS.startWorkflow()` for each independent fix (child workflows run in parallel), then `Promise.allSettled()` to await all.

### 4.5 Fix Validation Sub-Workflow

```
genFixWorkflow(vuln):
  ┌─ Step A: Gather context
  │   - Read vulnerable file(s) from repo
  │   - Extract function + 1 layer of cross-file deps
  │   - Retrieve similar fix patterns (RAG)
  │
  ├─ Step B: 🤖 Generate fix candidates (agentic)
  │   - LLM generates N candidate patches (N=3-5)
  │   - Output: structured FixCandidate[] via Zod
  │
  ├─ Step C: Validate each candidate (deterministic)
  │   for (candidate of candidates) {
  │     c1 = runStep(() => typeCheck(candidate))     // compile
  │     c2 = runStep(() => reScan(candidate))         // security
  │     c3 = runStep(() => runTests(candidate))       // functionality
  │     score = computeConfidence(c1, c2, c3)
  │   }
  │
  ├─ Step D: Select best candidate
  │   - Pick highest-confidence passing candidate
  │   - If none pass all 3 checks → retry Step B with feedback (max 3)
  │   - If still fails → mark as "manual-only"
  │
  └─ Return: { patch, confidence, validationResults }
```

### 4.6 Rollback Pattern

```
Post-merge monitoring (separate workflow):
  ┌─ Watch for: test failures, new alerts, incident reports
  │
  ├─ If regression detected within 24h:
  │   Step 1: Auto-create revert PR
  │   Step 2: Run CI on revert
  │   Step 3: If CI passes → auto-merge revert
  │   Step 4: If CI fails → escalate to on-call
  │   Step 5: Re-open original security alert
  │
  └─ Audit: log revert reason + link to original fix PR
```

|-------|----------------|---------|

| Triage decisions + reasoning | App DB | Explainability |

### 4.8 Agent Security: Protecting Against Exploitation

| Threat | Attack Vector | Mitigation |
|--------|--------------|------------|
| **Prompt injection via CVE description** | Malicious CVE text tricks LLM into generating backdoor code | Sanitize CVE text before prompt; use structured input (not raw text); validate output via re-scan |
| **Supply chain attack via suggested upgrade** | LLM suggests upgrading to a compromised package | Verify suggested package against allowlist; check npm audit / Socket.dev for the new version |
| **Dependency confusion** | Agent creates PR bumping to internal package name that exists on public registry | Scope checks; registry allowlist |
| **Excessive permissions** | GitHub App token has write access to all repos | Minimal GitHub App permissions; install only on target repos |
| **Fix introduces new vuln** | LLM-generated code has XSS/SQLi | Mandatory re-scan with multiple tools (majority vote: 2 of 3 detect = reject) |

### 5.1 Zod Schemas (TypeScript)

```typescript
// Scanner output (deterministic)
const ScanFindingSchema = z.object({
  id: z.string(),                    // "CVE-2026-1234"
  scanner: z.enum(["trivy", "semgrep", "npm-audit"]),
  severity: z.enum(["critical", "high", "medium", "low", "info"]),
  cvss: z.number().optional(),
  cweId: z.string().optional(),      // "CWE-79"
  package: z.string().optional(),
  currentVersion: z.string().optional(),
  fixedVersion: z.string().optional(),
  filePath: z.string().optional(),
  line: z.number().optional(),
  description: z.string(),
});

// Triage output (agentic — LLM fills reasoning)
const TriageResultSchema = z.object({
  prioritizedFindings: z.array(z.object({
    findingId: z.string(),
    adjustedSeverity: z.enum(["critical", "high", "medium", "low", "false-positive"]),
    reasoning: z.string().describe("Why this severity — reference code context"),
    exploitability: z.enum(["proven", "likely", "unlikely", "none"]),
    fixType: z.enum(["version-bump", "code-change", "config-change", "accept-risk"]),
  })),
  executiveSummary: z.string(),
  blockerCount: z.number(),
  recommendedAction: z.enum(["block-deploy", "warn-and-proceed", "informational"]),
});

// Fix candidate output (agentic — LLM generates patch)
const FixCandidateSchema = z.object({
  findingId: z.string(),
  fixType: z.enum(["version-bump", "code-patch", "config-change"]),
  confidence: z.number().min(0).max(1),
  explanation: z.string().describe("What the fix does and why it's correct"),
  changes: z.array(z.object({
    filePath: z.string(),
    originalCode: z.string().describe("Exact code to be replaced"),
    fixedCode: z.string().describe("Replacement code"),
  })),
  newDependencies: z.array(z.object({
    package: z.string(),
    version: z.string(),
  })).optional(),
  breakingChange: z.boolean(),
  testSuggestions: z.array(z.string()).optional(),
});

// PR description output (agentic — LLM writes narrative)
const PRDescriptionSchema = z.object({
  title: z.string().describe("[SECURITY] Fix CVE-XXXX in package-name"),
  body: z.string().describe("Markdown PR body with vulnerability details, fix summary, testing notes"),
  labels: z.array(z.string()),
  reviewers: z.array(z.string()).optional(),
});
```

## 8. Key Architectural Principles

1. **"The skeleton is deterministic, the brain is AI"** — Hardcoded rules bound what the agent can do; within those bounds, the AI decides tactics
2. **Governance as architectural input** — Not a compliance afterthought; build audit trails and approval gates into the workflow from day one
3. **Earned autonomy through demonstrated competence** — Start with Tier 2 (human review) for all fix types; graduate to Tier 1 (auto-merge) only after confidence calibration on your codebase
4. **Never trust verbalized confidence** — LLMs are miscalibrated when asked "how confident are you?"; use semantic clustering or validation-based confidence instead
5. **Multi-tool validation** — Majority vote (2 of 3 scanners detect = real vuln) for both detection and fix validation
6. **Small, focused PRs** — One vuln per PR (unless transitive chain); clear explanation of what/why/how in PR description
